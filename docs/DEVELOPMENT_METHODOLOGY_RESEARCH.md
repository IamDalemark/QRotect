## 1. Methodology: Agile, with iterative delivery

**Source title:** Manifesto for Agile Software Development. **URL:** https://agilemanifesto.org/

**Paraphrase:** Agile values collaboration, useful working software, interaction among people, and adapting to change. Processes, tools, planning, and documentation still have value. **QROTECT applicability:** Keep a prioritized list of requirements, produce reviewable features, consult intended users or reviewers, and adjust later work based on findings. Do not describe documentation as unnecessary.

**Source title:** Principles behind the Agile Manifesto. **URL:** https://agilemanifesto.org/principles.html

**Paraphrase:** The principles support frequent delivery, changing requirements, collaboration, technical quality, simplicity, and regular reflection on team practices. **QROTECT applicability:** A proposed cycle can select work, design and build it, test it, demonstrate it, gather feedback, reflect, and revise the backlog. These are project workflow choices, not a claim that the Manifesto mandates named phases. Agile alone does not establish that Scrum, formal Scrum roles, a particular sprint duration, or named Scrum events are being used. Those details require the researcher's confirmation.

## 4. Verification tools and measurement boundaries

**Vitest:** [Getting Started](https://vitest.dev/guide/) describes a Vite-powered testing framework. QROTECT's repository uses it for schema, search, phone-link, and offline-data logic tests. Test results must come from executed reports; a planned test is not a passing result.

**Playwright with axe:** [Playwright accessibility testing](https://playwright.dev/docs/accessibility-testing) documents browser testing with axe scans for automatically detectable accessibility issues. QROTECT can use browser workflows for navigation, filtering, confirmation, administrator flows, and offline behavior, and axe for automated accessibility checks. Automated scans are not proof of complete accessibility; supplement with keyboard, touch, screen-reader, and physical-phone review where applicable.

**Offline constraint:** [MDN Cache](https://developer.mozilla.org/en-US/docs/Web/API/Cache) documents browser request/response storage and notes storage limits and eviction. Combined with the repository's architecture, the accurate QROTECT claim is saved public access after a successful online visit and readiness checks. First-time offline access, permanent retention, fresh contacts while offline, and guaranteed service availability are not established.

**Phone handoff:** PRODUCT.md, README.md, and ARCHITECTURE.md establish that QROTECT activates a validated `tel:` link following explicit confirmation. It does not place, monitor, or certify connection of the call. Automated tests intercept links; physical checks should use a consenting number. A task-success measure can cover selecting the correct number and handing it to the phone application without asserting emergency dispatch occurred.

## 5. Diagram accuracy requirements

1. **Agile development procedure:** initial problem/literature/resource preparation, then a repeating planning–design–build–test–review/feedback–reflection loop. End with release preparation and maintenance; allow findings to return to the backlog. This is an adapted project workflow, not ADDIE or an assertion of Scrum.
2. **Use cases:** visitors browse/search/filter, choose language, read approved guidance/map, access saved data, and confirm phone handoff. Administrators authenticate, maintain drafts, preview, publish, inspect history, and restore. Visitors and administrators have different access boundaries.
3. **Architecture:** QR artwork encodes the site URL; the browser renders the public interface; Next.js reads validated publication data from Supabase; administrator actions use Auth and membership checks; storage holds map files; service worker/Cache API provide saved public access. The phone app is an external handoff. Vercel may be shown as proposed hosting, not already deployed.
4. **Physical ERD:** show `auth.users`, `administrators`, `directory_drafts`, `publications`, and `audit_events`. `administrators.user_id` is a PK/FK to `auth.users.id`, giving each Auth user at most one membership. Nullable `audit_events.actor` is an FK to `auth.users.id`, giving a user zero or many events. `directory_drafts` is a singleton working record with `payload jsonb` and `revision`; `publications` has immutable `snapshot jsonb` records and one current version. There is no SQL FK linking drafts to publications or audit-event revisions to the draft. Depict those associations as dashed operational relationships if needed, not declared relational constraints.
5. **Nested document inset:** contacts and their numbers, guidance, map metadata, and quick-call references are JSON content, not normalized SQL tables. Categories and service areas are fixed bilingual application definitions. A separate content-structure diagram may explain them without misrepresenting the ERD.
